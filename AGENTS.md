# AGENTS.md — guide for AI coding agents working on this repository

This file is the single source of truth for agent-facing instructions. Agent-specific files
(`CLAUDE.md`, `GEMINI.md`, `AGENT.md`, `.github/copilot-instructions.md`) are thin pointers here —
edit **this** file, not them.

## What this repo is

A fork of `bata24/gef` ([origin](https://github.com/MarcoApollonio02/gef), default branch `dev`):
a GDB plugin (GEF — GDB Enhanced Features) implemented as a Python package loaded into GDB's
embedded Python interpreter. It has been modularized from a single ~160k-line `gep.py` monolith
into the `gef/` package; the monolith no longer exists in this repo. **Operators work on branches
and open PRs against `dev`** — pushing to `dev` directly is protected by a repository ruleset.

## Repository structure

```

├── __init__.py         ← PEP-562 lazy re-exports of the public API
├── bootstrap.py        ← Gef/main() — wiring, auto-discovery, session start (Layer 4)
├── core/               ← domain + runtime state (Layers 0–1)
│   ├── runtime.py      ← registries (CommandRegistry/ArchRegistry), current_arch, path constants
│   ├── arch_base.py    ← the abstract Architecture contract every arch implements
│   ├── http.py         ← stdlib-only http_get   (must stay gdb-free)
│   ├── update.py       ← stdlib-only self-update (must stay gdb-free)
│   ├── memory.py       ← address/memory primitives (canonical home of is_*_link_list, p8..u128)
│   └── ...             ← address, process, elf, instruction, symbols, strings, types,
│                         qemu, auxv, events, unicorn, pagewalk, kernel, cache, color, display,
│                         config, errors, exec, hash, heap, syscall, utils, bitinfo
├── arch/               ← one file per architecture family (Layer 2)
└── commands/
    ├── base.py         ← GenericCommand, parse_args, register_command (Layer 2)

tests/
├── unit/               ← pytest tier (run outside gdb; collected by default)
├── gdb/                ← gdb-tier scripts (run with `gdb -q -nx -x <script>`)
```

Read `docs/ARCHITECTURE.md` before touching anything structural — it is the canonical reference
for the package layout, the layering rules, and the contributor walkthroughs.

## Hard rules (do not violate these)

1. **Layering.** Dependencies flow one way: `core → arch/commands → bootstrap`.
   - `core/` never imports `arch/*` or `commands/*` at module scope. Runtime-only cross-layer
     needs use a **function-local (late) import** inside the method that needs it.
   - `arch/*` never imports `commands/*`.
   - Commands may import `core`, `arch`, and `commands/base`; referencing a command in a sibling
     category must also be a lazy in-method import (e.g. inside `do_invoke`).
   - Commands (and `core/`) must never import `gef.bootstrap` (Layer 4).
2. **`current_arch` is never imported by name.** It is rebound by `set_arch()`; always access it
   as `runtime.current_arch`. In executable code there are **zero** bare `current_arch`
   references; occurrences inside help strings/comments are intentional and preserved.
   Enforce with:
   `grep -rn '\bcurrent_arch\b' gef/ --include='*.py' | grep -v 'gef/core/runtime.py' | grep -v 'runtime.current_arch' | grep -v '"' | grep -v "'"` → must print nothing.
3. **Registry access.** Use `runtime.CommandRegistry` / `runtime.ArchRegistry`; never create or
   reference module-level `__gef_command_instances__`-style globals.
4. **Family co-location.** An inheritance family of commands lives in one file.
5. **gdb-free modules.** `core/runtime.py`, `core/http.py`, `core/update.py` (and anything the
   pytest tier imports) must not `import gdb` at module level.
6. **Command metadata is the golden source.** `_cmdline_`, `_category_`, `_syntax_`,
   `_example_`, `_note_`, `_aliases_` on each command class generate `docs/COMMANDS.md`.
   If you add/remove a command OR touch any metadata, regenerate and commit the docs in the
   same change (see "If you changed commands" below). The golden test fails otherwise.
7. **Python floors:** Python ≥ 3.8 and GDB ≥ 9.2. No `match` statements, no PEP-604 `|`
   unions, no `tarfile.extractall(filter=...)`, no `zip(strict=)`.

## How to add a new command

1. Create `gef/commands/<category>/foo.py` (pick the existing category it belongs to — see the
   `# <nn>` sections of `docs/COMMANDS.md`).
2. Subclass `GenericCommand`, set metadata, implement `do_invoke`:

```python
from gef.commands.base import GenericCommand, parse_args, register_command

@register_command
class HelloCommand(GenericCommand):
    """Show a greeting."""

    _cmdline_ = "hello"
    _category_ = "07-d. Misc - Show Example"   # an existing category, verbatim
    _syntax_ = "hello"
    _example_ = "hello"

    @parse_args
    def do_invoke(self, argv):
        from gef.core.color import gef_print
        gef_print("hello")
```

3. That's it — no registry list to edit; the module is auto-discovered by `walk_packages` at
   boot. If you need symbols from `gef.core.*` or `gef.commands.base`, import at module scope;
   importing another *command* module must be lazy (in-method).
4. Extract an existing command only by **moving it verbatim** (no logic rewrites) plus adding
   imports — never re-implement logic during a move.

## How to add a new architecture

Create `gef/arch/foo.py`, subclass `Architecture` (from `gef.core.arch_base`), set
`load_condition`, and implement the abstract interface (see `docs/ARCHITECTURE.md` §4 for the
full checklist and an example). No registration needed — it is auto-discovered.

## How to test / verify

```bash
# fast unit tier (no gdb needed); use the repo venv if available
pytest tests/unit -q                    # or: .venv-dev/bin/python -m pytest tests/unit -q

# boot smoke (load everything from the package, no monolith)
gdb -q -nx -ex "source gef-bootstrap.py" -ex q           # expect: "GEF is ready", "Loaded 415 commands"

# gdb-tier checks
gdb -q -nx -x tests/gdb/test_phase1_checkpoint.py        # expect: PHASE1 CHECKPOINT PASS
gdb -q -nx -x tests/golden/test_commands_md.py           # expect: GOLDEN COMMANDS.MD PASS

# if you changed any command or its metadata: regenerate the golden reference and check it in
gdb -q -nx -ex "pi import sys; sys.path.insert(0,'.'); from gef import *; Gef.main()" \
    -ex "gef dump-commands docs/COMMANDS.md" -ex q

# installer edits: syntax check
sh -n install-uv.sh && sh -n install-no-uv.sh && sh -n install-minimal.sh
```

All of the above must pass before a change is called done. A green print is evidence; report the
actual output, not the intention that "it should work".

## Development workflow with AI agents (use the superpowers skills)

This repo is developed with the **superpowers** skills (available under `~/.agents/skills/`).
Follow them in this order when implementing anything beyond a one-line fix. The agent's own
provider environment should be treated as default (inherit the session model when launching
subagents).

1. **brainstorming** — before designing a feature. Understanding intent and tradeoffs first.
2. Write a **spec** in `docs/superpowers/specs/` and an **implementation plan** in
   `docs/superpowers/plans/` (both gitignored; local working documents).
3. **subagent-driven-development** — execute the plan by dispatching one fresh implementer
   subagent per task, then a task reviewer, with a fix loop capped at 5 rounds, and a final
   whole-branch review at the end. Track progress in a *ledger* at
   `.superpowers/sdd/<plan-name>/progress.md` (its first line must name the plan file) — it is
   what survives context compaction. Never skip a task review; never let an implementer review
   itself.
4. **verification-before-completion** — run the checks and paste real output; never claim green
   without having seen it.
5. **finishing-a-development-branch** — the merge/PR decision belongs to the human partner.

Never commit anything under `docs/superpowers/` or `.superpowers/` — both are gitignored
local scratch. Keep `gef.py` out of the tree; do not resurrect a monolith file. Hand-authored
edits of `docs/COMMANDS.md` are forbidden (it is generated).

When in doubt: read `docs/ARCHITECTURE.md` first, then `README.md`/FAQ for user-facing facts.
